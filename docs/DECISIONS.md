# Decisions

Why this system is built the way it is. One entry per non-obvious call,
written when the call is made — never reconstructed later. See
[`.claude/commands/build-authz-service.md`](../.claude/commands/build-authz-service.md)
rule 4: `PROGRESS.md` records state and goes stale; this file records
reasoning and stays true. If someone asks "why did you do it that way" and
the answer isn't here, the answer is already lost.

Entries D-001 through D-007 were settled while turning this repository from
its previous identity (a multi-tenant security kit) into this one, before
Phase 0 of the build spec starts for real. Later entries come from build
decisions and continue the numbering. Never delete an entry — supersede it
with a new one and mark the old one `superseded by D-0NN`.

## D-001 — Repurpose the isolation test suite as `.todo()` specs, not delete it and not half-implement it

**Date:** 2026-08-15 · **Phase:** 0 (pre) · **Status:** settled
**Decision:** The three files under `test/isolation/` restate the old tenant-isolation proof's exact assertions in ReBAC terms — real `describe`/`it.todo()` names, real doc comments, zero implementation. See `test/isolation/README.md` for the full mapping from old file to new.
**Alternative rejected:** (a) Delete the suite entirely and let Phase 1+ write tests from scratch. (b) Write real, passing tests now against a minimal implementation invented for the purpose.
**Why it lost:** (a) throws away the single most valuable thing inherited from the previous identity — a proven shape for proving a negative security property (no unauthorized path/row) three independent ways (real-database integration, differential/property fuzzing, hand-picked injection regression). Re-deriving that shape from nothing in a later phase is real, avoidable work, and worse, an easy shape to under-scope on a first pass. (b) violates the explicit instruction to write the build specification before any implementation code, and a minimal implementation invented just to make tests pass now would very likely not match what Phase 1–5 actually build, making the tests wrong by construction and require rewriting anyway.
**Revisit if:** Never. Un-skip each `.todo()` in the same change that implements what it needs — a `.todo()` staying red past its phase's stated exit criteria is itself a signal that phase isn't actually done.

## D-002 — Drop the npm-publish scaffolding entirely; this is a private deployed service, not a published library

**Date:** 2026-08-15 · **Phase:** 0 (pre) · **Status:** settled
**Decision:** Removed `.changeset/`, `CHANGELOG.md`, `CONTRIBUTING.md` (its content was the changesets release flow), `docs/versioning-policy.md` (semver promises about a `package.json` `exports` map that no longer exists), `.github/workflows/release.yml`, and every `package.json` field that only makes sense for a published npm package (`exports`, `typesVersions`, `main`/`module`/`types`, `files`, `publishConfig`). `package.json` now carries `"private": true`.
**Alternative rejected:** Keep the publish pipeline dormant/unused in case this ships to npm later.
**Why it lost:** A dormant release workflow referencing files that no longer exist (`CONTRIBUTING.md`, `.changeset/*`) doesn't fail loudly when it should — the exact failure mode `.claude/commands/build-authz-service.md` rule 9's spirit warns against elsewhere in this project's lineage (a tool that doesn't fail loudly on a broken assumption is worse than one that does). If this project is ever meant to ship as an installable library rather than a deployed service, that's a real, deliberate scope change worth its own decision entry — not a leftover.
**Revisit if:** A decision is made to publish a client SDK or CLI as an installable package — re-add the publish scaffolding fresh against that package's actual shape, don't resurrect this entry's deleted files.

## D-003 — Build with plain `tsc`, not `tsup`

**Date:** 2026-08-15 · **Phase:** 0 (pre) · **Status:** settled
**Decision:** `npm run build` is `tsc -p tsconfig.json`. `tsup.config.ts` is removed.
**Alternative rejected:** Keep `tsup`'s dual ESM/CJS + per-file compilation setup.
**Why it lost:** The previous identity's `tsup` config existed specifically to solve dual-package-hazard problems for a library with six independently-importable subpath exports sharing a module-level singleton (see that config's own removed comment, and `docs/versioning-policy.md`, also removed). None of that applies to a service with one deployment target and no public subpath API. `tsc` is simpler, already a dependency, and sufficient.
**Revisit if:** The project grows a published client package that needs dual-format output — evaluate `tsup` fresh against that package's actual constraints then, don't restore this config blind.

## D-004 — No ORM for the tuple store; hand-written SQL over `pg`

**Date:** 2026-08-15 · **Phase:** 0 (pre) · **Status:** settled
**Decision:** The Phase 2 tuple store and Phase 4 production check engine will query Postgres directly via `pg`, with hand-written SQL (including recursive CTEs for the graph walk), not an ORM/query builder.
**Alternative rejected:** Drizzle ORM (already a dependency of this repo's previous identity, for RLS-related type examples).
**Why it lost:** Mirrors the reasoning `.claude/commands/build-authz-service.md` §2 records for keeping soundness statistics in-repo rather than from a library: the recursive graph walk is the part of this project that must be exactly right and independently verifiable, and a query builder's abstraction over recursive CTEs is exactly the kind of layer that makes "what SQL actually ran" harder to audit, not easier — for the one query in this codebase where that audit matters most.
**Revisit if:** A concrete query-builder limitation blocks something the raw approach genuinely can't express cleanly — write that limitation down here before reaching for an ORM, don't reach for it first.

## D-005 — Soundness is proven by differential testing against a naive reference resolver, not asserted from the production resolver's own logic

**Date:** 2026-08-15 · **Phase:** 0 (pre) · **Status:** settled
**Decision:** Phase 3 builds a deliberately slow, deliberately naive in-memory BFS resolver whose only job is to be obviously correct. Phase 5 fuzzes random schemas/tuple graphs/queries and asserts the production (Phase 4) resolver agrees with it on every one — see `test/isolation/differential-soundness.fuzz.test.ts` and build spec §6.2.
**Alternative rejected:** Hand-derive a fixed set of expected results (from the Zanzibar paper's own worked examples, or authored by hand) and assert the production resolver matches them.
**Why it lost:** A fixed example set only proves the engine is correct on the examples someone thought to write down — exactly the "commodity eval script" failure mode a sibling project in this org's own build spec calls out for a different domain (a 30-prompt pass-rate script). Differential fuzzing against an independent, structurally different implementation finds the graph shapes nobody thought to hand-author, the same reason property-based fuzzing replaced hand-picked cases as the primary tool in this repo's own inherited `test/isolation/` suite.
**Revisit if:** Never, for the differential harness itself. Hand-derived examples still have a place (Phase 3's own exit criteria use a handful to sanity-check the reference resolver before it's trusted as an oracle) — they are a floor under the fuzz harness, not a substitute for it.

## D-006 — `false_grant` and `false_deny` are reported as distinct, asymmetric outcomes, never collapsed into one "mismatch" count

**Date:** 2026-08-15 · **Phase:** 0 (pre) · **Status:** settled
**Decision:** A differential-fuzzing divergence is classified as `false_grant` (production engine allowed, no path exists — a security bug, blocking) or `false_deny` (production engine denied, a path exists — a correctness bug, non-blocking). See build spec §6.5.
**Alternative rejected:** Report a single "divergence rate" and let a threshold decide pass/fail.
**Why it lost:** The two failure modes have entirely different consequences — one is an unauthorized permission grant, the other is an availability/correctness annoyance — and a threshold on a blended rate can pass a run that hides a real false grant behind a larger number of harmless false denies. This is the same reasoning a sibling project in this org's build spec applies to keeping `no_detectable_difference` and `insufficient_data` as distinct verdicts rather than one "inconclusive" bucket.
**Revisit if:** Never.

## D-007 — Environment loading uses `zod` + `dotenv`, not a dependency-free hand-rolled parser

**Date:** 2026-08-15 · **Phase:** 0 (pre) · **Status:** settled
**Decision:** `src/config/env.ts` parses `process.env` through a `zod` schema (coercion, enums, defaults, required-field messages) after `dotenv.config()`.
**Alternative rejected:** A small dependency-free `.env` line parser (the pattern a sibling project in this org uses for its CLI, where the env footprint is much smaller and dependency-freedom was itself the point for a tool meant to be trusted end to end).
**Why it lost:** This project's env footprint has real structure to validate — numeric coercion with bounds, enums, a mix of required and defaulted fields — that a line parser would either not validate at all or would re-implement `zod` poorly to cover. This is a service in the same shape as this org's other Postgres-backed services, which already use exactly this `zod` + `dotenv` pattern; matching it is the more defensible default than re-deriving a different one for no stated reason.
**Revisit if:** Never, absent a concrete reason `zod` itself becomes a liability (it is not in the soundness-critical path D-005 protects).

## D-008 — `DATABASE_URL` (and other blank-placeholder env vars) are optional at the schema layer; required at the point of use

**Date:** 2026-08-15 · **Phase:** 0 · **Status:** settled
**Decision:** `DATABASE_URL`, `ADMIN_API_KEY`, and `SOUNDNESS_FUZZ_SEED` are validated as optional, non-empty-if-present strings (empty string from a blank `KEY=` line in `.env` is treated as absent, not as a validation failure — see `optionalString()` in `src/config/env.ts`). Each command that actually needs `DATABASE_URL` (starting with `authz doctor`) checks for it itself and reports a command-specific, actionable error before touching Postgres.
**Alternative rejected:** Required, eagerly validated at module-import time (this repo's own original Phase 0 scaffolding, before Phase 0's own CLI work).
**Why it lost:** Caught live building `authz doctor`: eager validation crashes `authz --help` on a fresh clone with no `.env` at all, before commander even parses argv — directly contradicting this project's own Phase 0 exit criterion ("`authz --help` runs"). A CLI's help output must not depend on infrastructure the command being asked about doesn't need. Separately, `.env.example`'s own blank-value convention (`ADMIN_API_KEY=`) parses via `dotenv` as an empty string, not an absent key — a plain `z.string().min(1).optional()` rejects that exact shape, which is `.env.example`'s own placeholder convention rejecting itself. Both bugs were caught by actually running the CLI against a real `.env`, not by inspection.
**Revisit if:** Never for the optional-at-schema-layer shape. If a future command needs `DATABASE_URL` before argument parsing (unlikely — commander parses first by design), reconsider then, not preemptively.

## D-009 — `build` uses its own `tsconfig.build.json` with `rootDir: src`, separate from `typecheck`'s `tsconfig.json`

**Date:** 2026-08-15 · **Phase:** 0 · **Status:** settled
**Decision:** `npm run build` runs `tsc -p tsconfig.build.json` (`include: ["src/**/*.ts"]`, `rootDir: "src"`). `npm run typecheck` keeps using `tsconfig.json` (`include` covers both `src/**/*.ts` and `test/**/*.ts`, no emit) so tests still get full type-checking.
**Alternative rejected:** One `tsconfig.json` for both, as originally scaffolded.
**Why it lost:** Caught live running the built CLI (`node dist/cli/index.js`) during Phase 0's doctor CHECKPOINT: without an explicit `rootDir`, `tsc` infers the common root across every file `include` reaches — once `test/**/*.ts` is in that set alongside `src/**/*.ts`, the common root becomes the repo root itself, so `build` emitted to `dist/src/...` and `dist/test/...` instead of `dist/...`. That silently compiled the entire test suite into the distributable output (dead weight, never intended to ship) and broke `package.json`'s own `bin` entry (`./dist/cli/index.js`, which didn't exist — the real file was at `./dist/src/cli/index.js`). A single shared tsconfig for a project with both a `build` step and a `test` directory needs an explicit `rootDir` on whichever config emits, or this class of bug is silent until someone runs the built output directly.
**Revisit if:** Never.

## D-010 — Postgres hosting is Railway, in the org's existing `Upwork Portfolio` project, matching its `Postgres-<Service>` convention

**Date:** 2026-08-15 · **Phase:** 0/1 boundary · **Status:** settled
**Decision:** Provisioned a dedicated `Postgres-RBA` service inside the same Railway project (`Upwork Portfolio`) this org's other services already live in, using the identical `ghcr.io/railwayapp-templates/postgres-ssl:18` image and env-var shape (`POSTGRES_*`/`PG*`/`DATABASE_URL`/`DATABASE_PUBLIC_URL`) as `Postgres-ERP` — confirmed by reading that service's actual config rather than guessing. A TCP proxy (`yamanote.proxy.rlwy.net:36306`) exposes it publicly for CI and any dev machine with normal network access; the private `postgres-rba.railway.internal:5432` address is for anything eventually deployed inside the same Railway project.
**Alternative rejected:** A new, separate Railway project for this service; or a different Postgres provider entirely (Supabase, Neon, a managed RDS instance).
**Why it lost:** Build spec §2 states plainly that Postgres hosting only needs to be "any reachable Postgres" — the deciding factor is matching this org's own established pattern absent a stated reason to diverge, the same reasoning D-007 already applied to the env-loading library choice. A new project would fragment where this org's infrastructure lives for no benefit this repo needs.
**A real bug found provisioning it, not by inspection:** the raw image-based service didn't get the Railway-managed persistent volume the `postgres-ssl` entrypoint expects at `/var/lib/postgresql/data` — its own template flow provisions one automatically, but a service created directly via the image (bypassing that flow) doesn't. The container looped indefinitely logging `Railway volume not mounted to the correct path` instead of ever starting Postgres; the deployment reported `SUCCESS` the whole time, which would have looked fine from status alone. Fixed by explicitly creating and attaching a volume at that mount path before redeploying, then confirming via the deployment's own runtime logs that Postgres actually reached `database system is ready to accept connections` — not just that the deployment's status field said `SUCCESS`.
**Verification note:** this interactive session's own network policy proxies outbound HTTP(S) only — raw TCP to the Postgres wire protocol port is not reachable directly from here (confirmed: DNS resolves, `/dev/tcp` connect times out). `DATABASE_URL` was verified for real — actual auth, actual `select version()` — from a Railway-hosted sandbox (`sandboxCreate`/`sandboxExec` with `networkIsolation: PRIVATE`) instead, which reaches both the private and public-proxy addresses directly. This means later phases' own "verify by actually running it" standard (§0 rule 9, D-008/D-009's precedent) needs a real execution environment with outbound DB access — this session's shell isn't one — see the open question in `PROGRESS.md`.
**Revisit if:** This ever becomes a real production deployment with its own billing/ownership boundary separate from the org's other demo/portfolio services — reprovision fresh against that boundary, don't just relabel this one.

## D-011 — Rewrite-rule grammar: `&` binds tighter than `|`/`-`, left-associative, parentheses for explicit grouping

**Date:** 2026-08-15 · **Phase:** 1 · **Status:** settled
**Decision:** `permission edit = a | b & c` parses as `a | (b & c)`, matching the common SpiceDB/Zanzibar-adjacent convention. `|` and `-` share precedence and associate left-to-right (`a - b | c` is `(a - b) | c`). Parenthesized subexpressions are always allowed.
**Alternative rejected:** Equal precedence for all three operators, left-to-right only (no implicit `&` binding); or requiring parentheses whenever more than one operator kind appears in one expression.
**Why it lost:** §5's worked examples never mix operators in one expression, so nothing in the spec forces either choice — but implicit equal-precedence chaining of `&`/`|`/`-` left-to-right would make `a | b & c` mean `(a | b) & c`, which reads backwards to anyone who has used a boolean expression in any mainstream language. Matching the wider ecosystem's convention (intersection binds like AND, tighter than OR) is the more defensible default absent a spec-stated reason to diverge, the same reasoning D-007/D-010 already apply elsewhere in this project.
**Revisit if:** A real schema surfaces a rewrite rule where this precedence produces a result someone finds surprising in practice — parentheses are always available as an escape hatch in the meantime, so this is a low-cost decision to revisit.

## D-012 — Tuple-to-userset's target namespace check is strict; a plain relation subject type's is soft

**Date:** 2026-08-15 · **Phase:** 1 · **Status:** settled
**Decision:** `parent->view` (tuple-to-userset) always requires every namespace `parent`'s subject types can point to be present in the same compilation unit, or the compiler rejects it with `tuple_to_userset_unknown_namespace` — no exceptions. A plain relation subject type (`relation editor: user | group#member`) is checked only when `group` happens to be present in the same compilation unit; if it isn't, the `#member` suffix goes unverified rather than rejected.
**Alternative rejected:** Symmetric strictness — either both checks always require the target namespace present, or both skip the check when it's absent.
**Why it lost:** The two constructs have different jobs. Tuple-to-userset is compiled into a `RewriteRule` a resolver will _walk at runtime_ (§6.2/§6.4) — an unresolvable namespace reference baked into that tree is a defect the compiler can and must catch before it ever reaches a resolver. A relation's subject type is declaring what a _future tuple write_ is allowed to store; namespaces in this DSL are meant to be authored and compiled independently (this is exactly what lets `document.authz` and `org.authz` each compile standalone while only referencing `group#member`, without requiring every schema file in one compilation call) — so always requiring every referenced namespace to already exist in the same call would break that independence for no correctness benefit, since a tuple write against an actually-missing namespace is Phase 2's problem to reject at write time, not Phase 1's to reject at compile time.
**Revisit if:** Phase 2's tuple-write validation reveals that deferring this check creates a real gap (e.g. a subject type that's silently never checked against anything, ever) — tie the two phases' checks together explicitly then, rather than assuming Phase 2 alone closes it.

## D-013 — Circular-permission detection is a static compile-time graph check, not a per-branch liveness proof

**Date:** 2026-08-15 · **Phase:** 1 · **Status:** settled
**Decision:** The compiler rejects a permission whose definition depends, in a cycle, only on itself and other same-namespace permissions with no `relation` anywhere in the cycle to ground it (`permission view = view`; `permission a = b; permission b = a`). This is a static graph check over permission-to-permission `computedUserset` edges only — a `tupleToUserset` edge never counts toward a cycle, and a permission that has _any_ non-cyclic branch reaching a real relation (e.g. `permission x = a | y` where `a` is a relation and `y` cycles back to `x`) is still rejected as a whole, even though a runtime walk could resolve `x` via the `a` branch alone.
**Alternative rejected:** A per-branch liveness proof — reject only if _every_ path through the rewrite tree is unreachable, rather than rejecting the whole permission because _some_ path cycles.
**Why it lost:** A per-branch proof is real, extra graph analysis for a case the DSL author almost certainly didn't intend on purpose — a rewrite rule with a live, reachable branch and a dead, cyclic one sitting next to each other in the same `union` is far more likely a mistake (a copy-paste leftover, a typo'd permission name in the "wrong" branch) than a deliberate design, and staying conservative costs nothing but requiring the author to remove the dead branch explicitly. `tupleToUserset` edges are excluded from the cycle graph entirely because they're fundamentally different: following a real relation always makes progress against the actual tuple graph at runtime, and is already bounded by `CHECK_MAX_DEPTH` and cycle detection at the _data_ level (§6.4) — a compile-time graph over rewrite-rule _structure_ has nothing meaningful to say about a bound that only exists once real tuples are involved.
**Revisit if:** A real schema hits a legitimate, intentional case this rejects that a per-branch proof would allow — write down that concrete case here before loosening this, since the conservative default is deliberate, not an oversight.

## D-014 — `write_log.token` is a generated column equal to `id`, not an independently-tracked counter

**Date:** 2026-08-15 · **Phase:** 2 · **Status:** settled
**Decision:** `write_log`'s `token` column is `bigint generated always as (id) stored` — always, by construction, the same value as that row's own identity primary key. §6.3's own prose calls the token "`write_log.id`, monotonic"; §4's SQL lists `token` as a separate `not null` column. Rather than reconcile that by inserting the same value twice (which Postgres's identity-column mechanics make awkward — the identity value isn't known until the insert itself runs, so a second, independently-supplied `token` value could only ever drift from it), `token` is defined as a generated column so there is exactly one source of truth and the two can never disagree.
**Alternative rejected:** A second, manually-populated `bigint` column set to the same value the identity column will get, via a separate sequence read before insert, or by reading back `currval()` after.
**Why it lost:** Either approach introduces a real window where `id` and `token` could diverge (a failed/rolled-back insert consuming a sequence value; two sequences advancing independently under concurrent writers) for a value whose entire purpose is to be an unambiguous, monotonic marker every other part of this system trusts. A generated column makes divergence structurally impossible rather than merely unlikely — the same reasoning `types.ts` applies to keeping `relations` and `permissions` as separate maps so a name collision is impossible by construction, not just checked for.
**Revisit if:** Never, unless `write_log` needs a token value that legitimately differs from insertion order (e.g. batched writes sharing one caller-supplied token) — a real requirement that hasn't appeared yet.

## D-015 — `relation_tuples`'s uniqueness is enforced via `coalesce(subject_relation, '')`, not the literal `unique (...)` constraint §4 gives

**Date:** 2026-08-15 · **Phase:** 2 · **Status:** settled
**Decision:** The migration uses `create unique index ... (object_ns, object_id, relation, subject_ns, subject_id, coalesce(subject_relation, ''))` instead of a plain table-level `unique (...)` constraint naming `subject_relation` directly.
**Alternative rejected:** §4's literal SQL — a standard `unique` constraint across all six columns including the nullable `subject_relation`.
**Why it lost:** Postgres treats `NULL` as distinct from every other `NULL` under a standard `UNIQUE` constraint (`NULL = NULL` is unknown, not true), so two rows with identical `object_ns`/`object_id`/`relation`/`subject_ns`/`subject_id` and both `subject_relation IS NULL` would **not** collide — the literal §4 SQL only actually de-duplicates tuples that have a userset subject (`subject_relation` set), and silently allows duplicate rows for every plain-subject tuple, which is the overwhelming majority of real tuples (`user:alice` has no `#relation` suffix). This directly breaks §10's `writing-the-same-tuple-twice-is-idempotent-not-a-duplicate-row` for the common case. Found by reasoning about Postgres NULL semantics, then confirmed by actually inserting the same plain-subject tuple twice against a real database before trusting the fix (see `PROGRESS.md`) — exactly the "verify by running it" standard this project holds itself to elsewhere (D-008/D-009). `coalesce(subject_relation, '')` is safe as a sentinel because `''` can never be a real `subject_relation` value — every identifier must start with a letter (`IDENTIFIER_PATTERN`), so the empty string never collides with a real one.
**Revisit if:** Never, for this specific NULL-handling gap. If `relation_tuples` ever needs a `subject_relation` value that legitimately means something different from "absent" while still being falsy/empty, revisit the sentinel choice then.

## D-016 — `namespace_configs` is created in Phase 2, not deferred to whichever phase first uses it

**Date:** 2026-08-15 · **Phase:** 2 · **Status:** settled
**Decision:** Migration `0002` creates `namespace_configs` now, alongside `relation_tuples`/`write_log`. `checks` (Phase 6) and `soundness_runs` (Phase 5) are still deferred to their own phases.
**Alternative rejected:** Defer `namespace_configs` too, batching only what Phase 2's own stated exit criteria ("writing and reading round-trip; a write returns a strictly increasing token; deleting is immediately invisible to a post-delete-token read") strictly require — i.e. just `relation_tuples`/`write_log`.
**Why it lost:** `src/schema/dsl/types.ts`'s own doc comment (written during Phase 1, before Phase 2 started) states plainly: "`src/store/` (Phase 2) validates tuple writes against `NamespaceConfig.relations`." A tuple store that accepts a write for any `relation` string without checking it against a real, published schema can't actually enforce §5's own non-negotiable ("only a relation, never a permission, can be the target of a tuple write") at the one point that matters — write time; the DSL compiler enforcing it at compile time doesn't stop a caller from writing a tuple against a name the compiler never saw. `checks`/`soundness_runs` have no such forcing dependency from Phase 2's own code, so they stay deferred.
**Revisit if:** Never — this was always the design, just not decided explicitly until the tuple-write validation code made the dependency concrete.

## D-017 — Tuple _writes_ validate against the latest published namespace config; tuple _deletes_ don't

**Date:** 2026-08-15 · **Phase:** 2 · **Status:** settled
**Decision:** `writeTuple` rejects a write whose relation isn't declared (or is a permission, or the subject type isn't allowed) on the latest published `namespace_configs` row for that namespace. `deleteTuple` only validates identifier _format_ (§10's malformed-identifier requirement) — it never checks the relation or subject type against any published config.
**Alternative rejected:** Symmetric validation — reject a delete the same way a write would be rejected if it named an undeclared relation or disallowed subject type.
**Why it lost:** A namespace's schema can evolve — a relation present in version 1 might be removed in version 2. Tuples written under version 1 are still real, live facts in `relation_tuples` regardless of what the _current_ published config says, and revoking one of them must always be possible; a delete that fails because the relation "doesn't exist" in the _latest_ config would leave an unrevokable grant sitting in the store — the opposite of this project's own fail-closed posture (rule 10: no implicit grants). A write, by contrast, is creating a _new_ fact, and there is no such thing as "a stale version of the future" to defer to — validating a new write against anything other than the current schema wouldn't have a principled answer.
**Revisit if:** A future phase needs to validate a delete against the schema version that was live _when the tuple was originally written_ (not the latest) — that's a real, different feature (would need tracking which config version a tuple was written under), not a reason to make delete strict against the latest version.

## D-018 — Every `bigint` column read is explicitly `Number(...)`-coerced at the query boundary; no global `pg.types.setTypeParser`

**Date:** 2026-08-15 · **Phase:** 2 · **Status:** settled
**Decision:** `write_log.token`, `write_log.id`, and `relation_tuples.id` are all Postgres `bigint`. `pg` returns a `bigint` to JavaScript as a **string**, never coerced to `number` on its own — confirmed directly against a real database (`typeof result.rows[0].token === 'string'`), not assumed. Every function in `src/store/tuples.ts`/`src/store/tokens.ts` that reads one of these columns now explicitly wraps the raw value in `Number(...)` immediately, at the query boundary, before it's returned or compared to anything.
**Alternative rejected:** A single, global `pg.types.setTypeParser(20, parseInt)` registered once (e.g. in `src/store/client.ts`), relying on that module being imported before any bigint-returning query runs anywhere in the process.
**Why it lost:** Found by `test-author`'s own Phase 2 delegation, and it's a real, serious defect, not a display nit: `assertTokenObserved`'s `token > observed` compares two values with a plain `>`, which is lexicographic (string) comparison, not numeric, whenever both sides are still strings. That's silent for tokens with the same digit count (the common case in a short test run) and becomes a genuine correctness violation of §6.3's core guarantee — a token that was unambiguously already observed gets wrongly rejected — the moment the write counter crosses any digit boundary (`9→10`, `99→100`, ...), which any long-lived deployment will do routinely. Reproduced deterministically (not via a flaky "wait for 100 writes" approach) in `test/unit/store/tuple-store.integration.test.ts`. A global type-parser registration would fix it too, but only for callers that happen to import the module that sets it up first — exactly the implicit, import-order-dependent correctness this project already got burned by once (D-008: eager env validation crashing `authz --help` because of _when_ a module happened to run its top-level code, not _what_ it did). Explicit `Number(...)` at each read site is correct regardless of what else has or hasn't been imported yet, and it's visible in the function that actually needs it rather than living as an invisible prerequisite three files away.
**Revisit if:** A future column genuinely needs full 64-bit precision beyond `Number.MAX_SAFE_INTEGER` (~9 × 10^15) — none of `write_log`'s or `relation_tuples`' identity counters will realistically approach that in this project's lifetime, but if one ever might, that column needs its own explicit `bigint`-safe handling (e.g. a `string` type in the public interface), not a blanket coercion.

## D-019 — The Phase 2 integration suite starts its own ephemeral Postgres via testcontainers, not a hardcoded connection string

**Date:** 2026-08-15 · **Phase:** 2 · **Status:** settled

## D-020 — The reference resolver returns a result object, not a bare `boolean`, and deliberately omits a resolution path

**Date:** 2026-08-15 · **Phase:** 3 · **Status:** settled
**Decision:** `referenceCheck` returns `{ allowed: boolean }`, not a plain `boolean`. It does not return the tuple/rewrite chain that justified an `allowed` result, even though §6.7 states every `allow` decision must eventually be able to show its work, and the differential-fuzz test file's own wording anticipates "the full resolution path both resolvers took."
**Alternative rejected:** (a) Return a bare `boolean` — simplest possible shape. (b) Build resolution-path tracking into the reference resolver now, since it already walks the exact chain that would justify an `allow`.
**Why it lost:** (a) A result object costs nothing today and leaves room to grow (a `depthReached` diagnostic, eventually a resolution path) without a breaking-change signature later — cheap optionality, not premature abstraction, since Phase 4/5/6 are known to be coming and known to need richer output eventually. (b) Building the resolution path now is real, non-trivial complexity for no Phase 3 exit criterion: intersection and exclusion don't have one single linear witnessing chain (an intersection's "path" is really N paths, one per branch; an exclusion's is a path plus a _disproof_ of another path) — that's exactly the kind of design question Phase 6 (`expand()`, `checks.resolution_path`) is the right phase to settle deliberately, not something to bolt onto the "obviously correct" oracle under Phase 3's own time pressure. An oracle correct on the boolean question is still a fully valid oracle for Phase 5's differential fuzzing, which only needs agreement on `allowed`, not on matching resolution paths between two structurally different resolvers.
**Revisit if:** Phase 4's production resolver settles on its own return shape — confirm then whether the two need to agree on a resolution-path shape now, before Phase 5's divergence reporting is built around whatever shape exists at that point. Flagged explicitly by the `soundness-engineer` delegation as worth confirming before Phase 4 locks in its own interface.

## D-021 — Cycle detection is branch-local (path-relative), and the depth ceiling increments only when crossing to a new object or re-entering a name — never at every rewrite-rule combinator node

**Date:** 2026-08-15 · **Phase:** 3 · **Status:** settled
**Decision:** The reference resolver's `visiting` set tracks `(namespace, id, relation-or-permission-name)` triples on the _current root-to-node recursion path only_ — added on entry to the one shared recursion unit (`resolveMembership`), removed via `finally` right before that call returns. `union`/`intersection`/`exclusion` nodes recurse into their children over the _same_ object with no new depth increment and no new visited-set entry; only a leaf `computedUserset` (re-entering a name) or a namespace-crossing `tupleToUserset`/stored-userset-subject hop increments depth and adds a visiting-set key.
**Alternative rejected:** (a) A single global "ever visited" set spanning the whole check, not scoped to the current path. (b) Incrementing the depth counter at every rewrite-rule AST node visited, including `union`/`intersection`/`exclusion` combinators.
**Why it lost:** (a) would falsely flag a diamond-shaped DAG — the same `(ns, id, name)` legitimately reachable via two different, non-overlapping branches (e.g. two departments both nesting the same all-staff group) — as a cycle, denying a real grant that has nothing cyclic about it. Verified directly: a hand-built diamond case resolves correctly (allowed) against the actual implementation. (b) would make the depth ceiling sensitive to how large and deeply-nested a _schema's_ rewrite-rule tree happens to be, even though that tree is a finite, static, compile-time AST — already proven acyclic by the compiler's own `checkCircularPermissions` (D-013) — and has nothing to do with the _data_-driven recursion (crossing real tuple edges) that `CHECK_MAX_DEPTH`/this resolver's `maxDepth` actually exists to bound per §6.4. Counting combinator nodes would let a schema author's rewrite-rule authoring style (how many `|`/`&`/`-` operators they chain) eat into a budget meant for tuple-graph depth, for no correctness benefit.
**Revisit if:** A future schema construct makes the rewrite-rule tree itself capable of unbounded or dynamically-sized traversal (nothing in §5's grammar does today) — reconsider whether combinator nodes need their own bound then.

## D-022 — The reference resolver's isolation from the (not-yet-built) production resolver is enforced structurally, not just documented as a rule

**Date:** 2026-08-15 · **Phase:** 3 · **Status:** settled
**Decision:** `src/resolve/reference/resolver.ts` exports only `referenceCheck`, `EntityRef`, `ReferenceTuple`, `ReferenceCheckOptions`, `ReferenceCheckResult`, and `DEFAULT_REFERENCE_MAX_DEPTH` — every walking/evaluation helper (`resolveMembership`, `resolveRelation`, `evalRewrite`) is module-private. `ReferenceTuple` is a field-for-field redefinition of `src/store/tuples.ts`'s `TupleKey`, not an import of it. The file's only import is `src/schema/dsl/types.ts` (plain compiled-schema data shapes) — nothing from `src/store/`, `src/config/env.ts`, or any future `src/resolve/production/*`. A tiny exhaustiveness-check one-liner (`assertNeverRewriteRule`) is independently duplicated rather than imported from `src/schema/dsl/compiler.ts`'s own identical pattern.
**Alternative rejected:** A shared `src/resolve/graph-walk.ts` (or similar) utility module exporting a generic traversal function both the reference and production resolvers could import; or importing `TupleKey` directly from `src/store/tuples.ts` since the shape is identical anyway.
**Why it lost:** §6.2's own reasoning is explicit — "no shared code with the production resolver" exists specifically so a bug in the walking/evaluation logic can never be present in _both_ resolvers at once and therefore invisible to Phase 5's differential fuzzing (two independently-wrong implementations that happen to agree pass the harness identically, which is worse than either one being visibly wrong alone). A shared utility file is exactly the shape that failure mode would take: convenient today, and a silent, undetectable liability the moment Phase 4 exists and imports it too. Importing `TupleKey` from `src/store/` would also pull a database-shaped type (and, transitively, anything `src/store/tuples.ts` itself imports) into a module whose entire value proposition is being independently, obviously correct with zero I/O — even an unused transitive import chain is the wrong shape for a file meant to be trivially auditable in isolation.
**Revisit if:** Never for the shared-utility prohibition. If `TupleKey` and `ReferenceTuple` ever drift out of sync by accident (a field added to one, not the other), that's a real bug to fix by hand in both places — not a reason to unify them via a shared import.

## D-023 — The cycle-detection key's `\0` separator is written as the two-character escape `\0`, not a literal raw NUL byte

**Date:** 2026-08-15 · **Phase:** 3 · **Status:** settled
**Decision:** `resolveMembership`'s composite cycle-detection key (`` `${ns}\0${id}\0${name}` ``) uses the literal source text `\0` (backslash, zero — a valid JS/TS escape sequence the runtime turns into an actual null character) inside the template literal, never a raw NUL byte sitting directly in the file's bytes.
**Alternative rejected:** Nothing, structurally — this corrects what `soundness-engineer`'s delegation actually produced: the file as first written contained a literal, raw `0x00` byte at that position (same runtime string value, different on-disk encoding).
**Why it lost:** A raw NUL byte in a source file isn't just a style nit — `git` treats any blob containing a NUL byte in its first ~8000 bytes as binary. Confirmed directly: `git diff` against the original commit showed `Binary files ... differ` instead of a readable diff, which would have made this file's GitHub PR review show no diff at all — a direct contradiction of this project's own "the PR diff is the record" expectation, and a file effectively un-reviewable by anyone reading the PR rather than checking out the branch. Caught by actually running `git diff`/`git show` against the committed file, not by reading the source (the raw byte rendered as an ordinary-looking space in this session's own file-reading tool, and was only found by checking the file at the byte level after `test-author`'s report mentioned tooling trouble matching against it). The underlying design idea — a delimiter that can never appear in a real namespace/relation/id value, so a composite string key can't collide by accident — is sound and kept; only the on-disk encoding changed.
**Revisit if:** Never. If a future composite key needs an unambiguous separator again, use the same escape-sequence form, not a raw control byte, as a matter of course.

## D-024 — A "does this terminate" test must force a depth budget the independent depth ceiling can't itself satisfy, or it can't actually prove cycle detection works

**Date:** 2026-08-15 · **Phase:** 3 · **Status:** settled
**Decision:** `a-cyclic-group-nesting-terminates-and-resolves-denied` (`test/unit/resolve/reference-resolver.graph-shape.test.ts`) passes an explicit, very large `maxDepth` (1,000,000) rather than relying on `referenceCheck`'s default (1,000), specifically so a resolver with cycle detection completely removed would fail this test loudly (stack overflow / timeout) instead of accidentally passing.
**Alternative rejected:** Testing the cyclic case against the resolver's default `maxDepth`, on the reasoning that "it terminates and denies" is the whole claim and the default budget is what real callers actually use.
**Why it lost:** Found live, by `test-author`'s own fail-check discipline: with cycle detection _fully disabled_ in a deliberately-broken copy of the resolver, a version of this test using the default 1,000-depth ceiling still passed — the independent depth backstop (§6.4's _other_, unrelated termination guarantee) silently absorbed the infinite recursion the cycle detector was supposed to catch, before the assertion ever ran. A test with the right expected boolean and the right "did it hang" framing can still have zero actual power to catch the exact bug it claims to guard against, if a second, unrelated safety net happens to produce the same observable outcome. This is the same category of lesson §0 rule 9 and D-005 already state for the differential-fuzz harness as a whole ("a check engine that reports 'allowed' without that claim having been fuzzed... is worse than one that reports nothing") — a test is only as trustworthy as its own demonstrated ability to fail, and that has to be checked directly, not assumed from the test reading correctly.
**Revisit if:** Never for this specific test. This is worth carrying forward explicitly into Phase 5's fuzz-harness design (`docs/DECISIONS.md`'s own cross-reference, not a new decision yet): any fuzz/property test whose job is specifically to prove cycle detection has power — as opposed to overall termination — needs the same discipline, forcing a depth budget large enough that the depth ceiling can't be the thing doing the actual work.

## D-025 — The production resolver splits its walk across two genuinely different implementation strategies, not just two different files

**Date:** 2026-08-15 · **Phase:** 4 · **Status:** settled
**Decision:** `src/resolve/production/resolver.ts` handles rewrite-rule tuple-to-userset (`parent->view` and the union/intersection/exclusion combinators) via TypeScript-orchestrated recursion (`resolve`/`evalRewrite`), and stored-tuple userset-subject membership (nested group-style closures) via a single `WITH RECURSIVE` SQL query per relation-level check (`sqlRelationMembership`) — a genuinely different algorithm shape from the reference resolver's uniform in-memory array scan, not just a different codebase implementing the same algorithm in a different language.
**Alternative rejected:** Do the entire walk in TypeScript, issuing one `SELECT` per tuple lookup the way a literal transliteration of the reference resolver's structure would (many small queries, app-level closure computation over the results).
**Why it lost:** Two reasons, one mechanical and one about what makes differential fuzzing actually valuable. Mechanically: rewrite rules are schema-driven — an arbitrary compiled `RewriteRule` tree varies per namespace, so it can't be expressed as one static SQL query the way "follow every userset-subject tuple sharing this frontier" can, since that second problem's edge shape is schema-agnostic (D-004's own reasoning for why recursive CTEs belong in this project at all). More importantly: §6.2 values two _independent_ implementations agreeing, and "independent" is a stronger property when the two don't even share an algorithm shape, not just different source files following the same one. A bug specific to naive full-scan traversal (Phase 3's approach) and a bug specific to SQL-side transitive-closure computation (this file's approach) are unlikely to be the _same_ bug — which is exactly the property that makes agreement between the two meaningful evidence, not two coats of paint on one algorithm.
**Revisit if:** Never. If a future phase needs the production resolver to also handle mechanism 1 in SQL for performance reasons, that's a real, separate optimization decision — write it down here when it happens, weighing the isolation-value tradeoff explicitly rather than assuming performance wins automatically.

## D-026 — Two independent cycle-safety mechanisms in the production resolver, deliberately not unified into one

**Date:** 2026-08-15 · **Phase:** 4 · **Status:** settled
**Decision:** The production resolver has two separate cycle guards: a TypeScript-level `visited: Set<string>` (branch-local, add-on-entry/remove-on-exit via `finally`) catching tuple-to-userset cycles that cross objects, and a SQL-level `path` array column inside `sqlRelationMembership`'s recursive CTE catching userset-subject nesting cycles entirely within one query. Postgres's `WITH RECURSIVE` does not terminate on its own against a cyclic graph — this was verified by deliberately removing the SQL-side path-array guard and confirming the query actually hangs against a real seeded cycle (both by the `soundness-engineer` delegation and independently reproduced by the main agent with a hard OS-level timeout before this was accepted).
**Alternative rejected:** One shared cycle-tracking structure threaded through both the TypeScript recursion and passed into the SQL query as a parameter (e.g. an array of already-visited keys passed in and checked against inside the CTE).
**Why it lost:** The two recursions walk genuinely different graphs — tuple-to-userset hops between distinct `(namespace, id)` objects driven by rewrite-rule structure, versus userset-subject nesting within one relation's transitive-membership closure — and a cycle can only ever exist within one of those two graphs at a time, so there is no scenario needing cross-talk between the two guards. Threading a shared structure through the pool-query boundary would add real complexity (serializing a JS `Set` into a SQL array parameter on every call, keeping it in sync) for a case that provably cannot occur, since the two recursions never call back into each other mid-cycle.
**Revisit if:** A future rewrite-rule kind or a future stored-tuple shape ever creates a data path where the two recursions _can_ call back into each other before either completes — reconsider then, with a concrete graph shape that demonstrates the gap.

## D-027 — A naive "did the query return fast" test can pass with zero cycle protection, if the query planner prunes the whole join first

**Date:** 2026-08-15 · **Phase:** 4 · **Status:** settled
**Decision:** Every cyclic-graph test against the production resolver seeds a decoy tuple for the checked subject somewhere else in `relation_tuples`, unrelated to the cycle being tested — forcing the recursive CTE to genuinely traverse the cyclic subgraph rather than short-circuit.
**Alternative rejected:** Testing cycle termination with the checked subject appearing nowhere in the tuple table at all (the simplest possible fixture).
**Why it lost:** Found live by the `soundness-engineer` delegation, independently reproduced: Postgres's query planner can prune the entire recursive join up front when the checked subject never appears anywhere in `relation_tuples` — an empty-relation short-circuit at the planning stage, before the recursive CTE's own cycle guard (or lack of one) is ever actually exercised. A "cyclic case resolves fast" test built this way passes identically whether the path-array guard is present, absent, or entirely deleted — exactly the same failure mode D-024 records for the reference resolver's depth-ceiling-masking-cycle-detection trap, one layer down: a termination test's power depends on what it actually forces the system to do, not on the boolean or timing outcome alone.
**Revisit if:** Never for this specific fixture shape. Flagged, same as D-024, as a concrete lesson for Phase 5's fuzz-harness design: a fuzzed cyclic-graph query must seed the queried subject as a real, existing tuple elsewhere in the graph, or a soundness run can "prove" cycle-termination against the production SQL path without ever really exercising the guard that's supposed to provide it.

**Decision:** §3's repo layout lists `cache.ts` alongside `resolver.ts`/`cycles.ts` under Phase 4, but this phase does not build it. `CHECK_CACHE_TTL_MS` stays at its default of `0` (disabled).

## D-029 — A cyclic-termination test must assert on elapsed time, not just the returned boolean, because the depth ceiling alone can eventually produce the correct answer far too slowly to call "terminates"

**Date:** 2026-08-15 · **Phase:** 4 · **Status:** settled
**Decision:** `both-resolvers-deny-a-cyclic-group-nesting-and-terminate-...` and its sibling tests assert both the correct `allowed: false` value **and** a bounded elapsed time, and — beyond that — this project treats "the depth ceiling can quietly stand in for a missing cycle guard" as a fact to design tests around, not a hypothetical.
**Alternative rejected:** Trust a correct boolean result, with a generous timeout, as sufficient proof cycle detection works (the SQL path-array guard specifically, as distinct from the independent depth cap covered by D-024/D-027).
**Why it lost:** Confirmed live during `test-author`'s Phase 4 delegation: with the SQL-level path-array cycle guard removed but the depth cap left in place and bounded to 20,000, `sqlRelationMembership` against the real seeded two-node cycle still eventually returned the _correct_ boolean — `false` — but took **~49 seconds** to do it, versus milliseconds with the guard intact. A depth ceiling is a valid, independent termination guarantee (§6.4) — it will always eventually stop a bounded-but-unguarded recursive CTE — but "eventually terminates with the right answer" and "terminates fast enough to be a production check engine" are different claims, and only the second one is what a real cycle guard is supposed to provide. A test that only asserts the boolean, however generous its timeout, cannot distinguish "cycle detection works" from "cycle detection is silently absent and the depth cap alone paid for it at 10,000x the cost." This is now the third instance of the same family of lesson this project keeps re-deriving at each new layer (D-024 for the reference resolver's own depth ceiling, D-027 for query-planner pruning) — worth stating plainly as its own principle rather than only as three separate footnotes: **a termination test proves nothing about the specific mechanism it claims to test unless it can demonstrably fail when that specific mechanism, and only that mechanism, is broken.**
**Revisit if:** Never. Any future recursive-graph mechanism this project adds should have its own termination test checked against this same standard before being trusted — deliberately break the guard being tested, confirm the test goes red (slow or wrong, not just "eventually right"), then restore.

## D-031 — `critical` is fuzz-harness metadata the Phase 5 generator attaches to a namespace, not a DSL/schema feature

**Date:** 2026-08-15 · **Phase:** 5 · **Status:** settled
**Decision:** `GeneratedNamespaceMeta.critical` is a boolean the fixture generator assigns per generated namespace (the always-critical "protected resource" role namespace, plus each extra namespace independently and deterministically critical ~25% of the time), tracked only inside `src/soundness/generators.ts`'s own output and consumed only by `runner.ts` (to build the `criticalNamespaces` set) and `classify.ts` (to tag a `false_grant`'s `critical` field). Nothing in `src/schema/dsl/*` — the parser, the compiler, the compiled config shape, `namespace_configs` — knows this concept exists.
**Alternative rejected:** A `critical` modifier on the `namespace` declaration itself in the DSL grammar (e.g. `critical namespace document { ... }`), compiled into `namespace_configs.config` alongside relations and permissions, so a real schema author could flag a namespace as security-sensitive the same way they declare a relation.
**Why it lost:** §5 (the actual Phase 1 DSL grammar this project settled on) has no such construct, and reopening it now — mid-Phase-5 — to add one would be exactly the kind of scope creep §9's phase discipline exists to prevent: a real DSL feature needs its own compiler support, its own validation rules, its own versioning story in `namespace_configs`, and its own place in `docs/RELATIONS.md`, none of which this phase's exit criteria call for. §6.5's prose ("a namespace flagged critical in its schema") reads as if this were schema-level, but the actual requirement — "a false_grant on this namespace should be called out as especially severe when reporting a fuzz run" — is fully satisfiable as fuzz-harness-only metadata, since the only consumer of `critical` anywhere in this codebase is the soundness report itself. If a real caller ever needs to mark a production namespace as security-critical for some purpose _other_ than fuzz reporting, that's new scope for a later phase to design properly, not a retrofit onto Phase 5's generator.
**Revisit if:** A future phase needs "critical" to mean something to a real running check (e.g. gating an API response, or driving a production alert) rather than only shaping how a `soundness_runs` report reads — at that point it becomes a real schema concept and belongs in the DSL, with its own compiler and migration story.

## D-032 — Fixture coverage is guaranteed by construction, then independently re-audited against the compiled artifact — never trusted from the generation logic alone

**Date:** 2026-08-15 · **Phase:** 5 · **Status:** settled
**Decision:** `generateFixture` builds every fixture from three fixed-role namespace sources (`buildGroupNamespaceSource`, `buildHierNamespaceSource`, `buildResourceNamespaceSource`) that between them hand-place all four `RewriteRule` kinds (union, intersection, exclusion, tuple-to-userset — twice, actually, via two independent `->` rewrites) and exactly one guaranteed userset-subject cycle, regardless of what the seed's random draws do elsewhere in the schema. Separately, `computeCoverageReport` re-derives `RewriteRuleKindCoverage` and `hasCycle` by walking the _compiled_ schema (`compileSchema`'s output) and the _actual generated tuple array_ — not by reading back the construction logic's own intent — and `CoverageReport.ok` (which `computeVerdict` treats as a hard gate for the `insufficient_coverage` verdict) is only ever `true` if that independent walk actually finds all four kinds and a real cycle.
**Alternative rejected:** Trust the fixed-role construction alone — since the three core namespace sources are hand-written to always include every rewrite-rule kind and the cycle, treat "coverage achieved" as a property guaranteed by the generator's own code without a separate audit pass.
**Why it lost:** "The code that writes the fixture believes it wrote good coverage" and "the fixture that got compiled and published actually has that coverage" are different claims, and only the second is what `insufficient_coverage` is supposed to protect against. A bug in the hand-written namespace-source strings (a typo turning `parent->view` into a syntax the compiler silently treats differently, an off-by-one dropping the second `cycleB` tuple) would make the _construction_ logic still believe it achieved full coverage while the _compiled, published, actually-queried_ schema silently didn't — exactly the kind of self-reported-but-unverified claim this project's own build spec (rule 9) says is worse than reporting nothing. Independently re-auditing against the compiled artifact and the real tuple array is cheap (both are already produced for real I/O anyway) and turns "coverage by construction" from an assumption into a checked fact every single run, not just at generator-design time.
**Revisit if:** Never for this two-layer structure. If a future rewrite-rule kind is added to the DSL, both the construction (hand-placing an example of it) and the audit (`RewriteRuleKindCoverage` gaining a field for it) need to change together — a coverage kind added to one without the other is a silent gap in exactly the shape this decision exists to prevent.

## D-033 — Every generated namespace name carries a seed-derived salt, to prevent one run's stale tuple from producing a spurious `false_grant` in an unrelated later run

**Date:** 2026-08-15 · **Phase:** 5 · **Status:** settled
**Decision:** Every generated namespace name is `${word}_${salt}` where `salt = hashSeedToInt31(seed).toString(36)` — a small FNV-1a hash of the run's own seed, base-36 encoded. `user:*` subject ids are deliberately left unsalted (see below).
**Alternative rejected:** Draw namespace names straight from the small word bank (`doc`, `folder`, `group`, etc.) with no per-run modification, relying on the seed only to determine which words and how they're wired together.
**Why it lost:** Found by `soundness-engineer` before it could ever produce a false finding, not after: `relation_tuples` has no per-run partition — it's one live, unpartitioned table the production resolver always reads in full. Two different seeds' fuzz runs are entirely capable of independently drawing the same small-word-bank namespace name (e.g. both pick `doc` as namespace #2's name). Without salting, a tuple written by an _earlier_ run under that name would still be sitting in `relation_tuples` when a _later_, unrelated run reuses the same name — visible to the production resolver (reads the live table) but structurally invisible to that later run's reference resolver (which only ever sees its own in-memory `fixture.tuples` array, by design, per D-020/D-022's isolation). That mismatch is a real divergence by `classifyResult`'s own definition, but it's an artifact of cross-run table reuse, not a bug in either resolver — a false `false_grant`, exactly the kind of noise that would erode trust in every real finding this harness produces. Salting every namespace name from the run's own seed makes that collision effectively impossible without needing to truncate or partition `relation_tuples` between runs.
**Why `user:*` ids stay unsalted:** subject ids for the `user` namespace are deliberately left as-is (not `${word}_${salt}`) — a `user:*` subject never has tuples granting _it_ permissions written by the generator in a way that could collide with another run's meaning, and leaving them unsalted keeps hand-derived fuzz-replay seeds/queries more readable without reintroducing the collision risk that only applies to namespace names appearing as the _object_ side of a tuple.
**Revisit if:** `relation_tuples` ever gains per-run partitioning or the harness starts truncating between runs — at that point salting is redundant defense-in-depth rather than the only thing preventing this class of false finding, and could be simplified away if it costs real readability.

## D-034 — `fast-check` is used only as a seeded PRNG integer stream, never via its own composed arbitraries or shrinking

**Date:** 2026-08-15 · **Phase:** 5 · **Status:** settled
**Decision:** `generators.ts` calls `fast-check`'s `sample(integer(...), { seed, numRuns })` once, up front, to draw a large pool of deterministic integers from the seed, then hands that pool to a hand-rolled `SeededRng` class (`nextInt`/`nextIntBetween`/`nextBoolean`/`pick`/`shuffle`) that the rest of the generator draws from. No `fc.record`, `fc.array`, or any other composed arbitrary is used, and `fast-check`'s shrinking is never invoked anywhere in this file.
**Alternative rejected:** Use `fast-check` the conventional way — compose arbitraries (`fc.record({ namespaces: fc.array(...), tuples: fc.array(...), ... })`) to describe the shape of a fixture, and let `fast-check` generate (and, on a failing property, shrink) instances of it directly.
**Why it lost:** `fast-check`'s arbitraries and shrinking exist to answer "generate broadly across the possibility space, and when a property fails, find the smallest input that still fails it" — the right shape for property-based testing of a function whose _correctness_ is being questioned. Phase 5's generator has a different, narrower job: §6.8 requires that a fixture be "reproducible byte-for-byte from `graph_seed` alone," and — more specifically — this project's actual coverage requirement (D-032) demands _guaranteed_, not merely likely, placement of all four rewrite-rule kinds and a cycle in every single fixture, regardless of what the seed happens to roll. An arbitrary-composed fixture would make coverage probabilistic (a `fc.array` might, by chance, never emit an `exclusion` rule for a given seed) and would invite `fast-check` to shrink a _found divergence_ toward "simpler," which is the wrong instinct here — a soundness divergence should be reported and replayed exactly as generated (the run that found it), not minimized into a different, smaller fixture that may no longer reproduce the same bug. Using `fast-check` purely as a `pure-rand`-backed deterministic integer source keeps the one property actually needed (seed in, identical numbers out, every platform, every run) while keeping full hand-authored control over fixture _shape_ and guaranteed coverage.
**Revisit if:** A future phase adds a genuine "does this property hold across a broad random space" test where minimal-counterexample shrinking is actually the right tool (e.g. testing the DSL parser's own robustness against malformed input) — that's a legitimate, different use of `fast-check` and would live in its own test file, not inside this fixture generator.

## D-035 — A missing SQL cycle guard is structurally invisible to boolean-only differential fuzzing, at any depth setting — this is a known, accepted division of labor with the targeted Phase 3/4 termination tests, not a gap in Phase 5

**Date:** 2026-08-15 · **Phase:** 5 · **Status:** settled
**Decision:** The Phase 5 differential fuzzer is not relied on to catch a missing or broken SQL-level cycle guard (D-026's path-array guard inside `sqlRelationMembership`'s recursive CTE). That bug class stays covered exclusively by the targeted, elapsed-time-asserting termination tests already built in Phase 3 and Phase 4 (D-024, D-027, D-029). `runSoundnessFuzz`'s `maxDepth` option (a generic replay/reproduction knob — see its doc comment in `runner.ts`) is explicitly documented as _not_ a fix for this gap.
**Alternative rejected:** Treat this as a fuzzer gap to be closed — e.g. by forcing a very large `maxDepth` on fuzz runs (or a dedicated high-depth fuzz pass) so that a missing cycle guard's latency blowup would, at some sufficiently large depth, eventually manifest as a boolean divergence the classifier could catch.
**Why it lost:** Tested directly, not assumed. With the SQL path-array guard deliberately removed (same deliberate-break method as D-026/D-029) but the independent depth cap left in place, a full differential fuzz run — first by `soundness-engineer` at the standard production-realistic depth, then independently by the main agent forcing `maxDepth: 20_000` on a 500-query run — never produced a single `false_grant` or `false_deny`. The forced-high-depth attempt didn't even finish: it exceeded 300 seconds and was killed, because forcing a large depth cap applies to _every_ query in the batch, not just the ones that would exercise the cycle, so the run becomes impractically slow long before any depth is "large enough" to matter. This confirms the deeper reason, not just the practical one: removing the path-array guard while leaving the depth cap intact changes only the recursive CTE's _cost_ (D-029 measured ~49 seconds vs. milliseconds for a single query) — the _boolean it eventually returns is unchanged_, because the depth cap alone is still a valid, if catastrophically slow, termination guarantee (§6.4). `classifyResult` compares only `referenceAllowed`/`productionAllowed` booleans; a defect that corrupts only latency, never the boolean, is by construction invisible to it, at any depth, no matter how long a run is willing to wait. This is the same "termination test proves nothing about the mechanism unless it can fail" family as D-024/D-027/D-029, arriving at its natural conclusion: boolean-only differential comparison and elapsed-time-asserting targeted unit tests are testing two different properties (agreement vs. termination-speed), and no amount of scaling the first ever substitutes for the second.
**Revisit if:** The fuzz harness starts recording per-query latency (not just the boolean) and comparing it against a bound — at that point a latency-blowup bug like this one _would_ become fuzzer-visible, and this decision should be revisited alongside whatever design that latency-comparison feature needs. Until then, this is a stated, deliberate division of labor, not an open gap: report it as such in the Phase 5 CHECKPOINT.

## D-036 — The resolution path is a real evidence tree with a symmetric NEGATIVE witness for exclusion, not a linear breadcrumb list or a trusted boolean

**Date:** 2026-08-15 · **Phase:** 6 · **Status:** settled
**Decision:** `ReferenceCheckResult.path`/`ProductionCheckResult.path` (present iff `allowed`) is a `ResolutionStep` tree: `union` records the one branch that succeeded; `intersection` records every branch's own proof; `tupleToUserset` records the followed tuple and the proof at its target; and — the case D-020 explicitly deferred — `exclusion` records a proof of `base` **and** a `DisproofStep`, a structurally symmetric negative-witness tree proving `subtract` does not hold (a `relationDisproof`/`RelationDisproof` accounting for every real tuple examined, a `unionDisproof` needing every child disproven, an `intersectionDisproof` needing only one, and `boundReached`/`undeclared` leaves for a legitimately cycle- or depth-cut-off branch). Both resolvers export their own, field-for-field-independent copy of this whole shape (never a shared type), per D-022's precedent.
**Alternative rejected:** (a) A flattened `EntityRef[]` chain matching only §8's simplest worked example (union/tuple-to-userset), with intersection/exclusion collapsed to "here's the boolean, trust it." (b) Recording only the `base` proof for an exclusion and treating "subtract disproof" as an internal implementation detail never exposed.
**Why it lost:** (a) cannot express what an intersection or exclusion actually proved — a flat chain has no way to represent "N branches, all required" or "this branch and NOT that one," so it would either be wrong for those two rewrite kinds or silently omit them from having a real path at all, which fails Phase 6's own exit criterion ("every allow, ... contains a path that independently re-verifies," no carve-out for two of the four rewrite-rule kinds). (b) is exactly the shape §6.7/this task's own framing warns against: a verifier that has to trust "the resolver says subtract was false" isn't independently re-verifying anything, it's trusting the same resolver whose soundness claim is in question — the entire reason a `false_grant` differential-fuzz finding is credible (§6.2) is that nothing about it depends on trusting the system being checked, and a resolution path that quietly reintroduces that trust for exclusion would undermine the same principle one layer up. The disproof tree costs real code (see `resolveRelation`/`evalRewrite`'s exclusion case, and the production resolver's `RelationDisproof` closure-certificate variant) but keeps the whole path — including its hardest case — checkable by pure structural validation, never search, per the independent verifiers in `test/unit/resolve/reference-resolver.resolution-path.test.ts` and `test/unit/resolve/production/production-resolution-path.integration.test.ts`.
**Revisit if:** A future rewrite-rule kind is added to the DSL — it needs both a proof and (if it can appear inside an exclusion's `subtract`) a disproof shape designed with the same rigor, not bolted on as an afterthought.

## D-037 — The production resolver's relation-membership disproof is a flat reachability certificate, never a nested tree matching the reference resolver's shape

**Date:** 2026-08-15 · **Phase:** 6 · **Status:** settled
**Decision:** `RelationDisproof` (production) is `{ object, relation, maxDepth, nodes: ClosureNode[] }` — every frontier node `sqlRelationMembershipWithWitness`'s recursive CTE actually reached, each carrying its own real tuples, depth, and root-to-here ancestor path — rather than mirroring the reference resolver's recursive `relationDisproof`/`tupleDisproofs` tree shape field-for-field.
**Alternative rejected:** Force both resolvers' relation-level disproof into the identical nested-tree shape, reconstructing it in TypeScript via repeated round-trips into Postgres (one query per nesting level, mirroring the reference resolver's own recursive scan).
**Why it lost:** The reference resolver's nested disproof falls out for free from a scan that was already going to touch every tuple in memory. The production resolver's relation-membership mechanism is one recursive SQL query that computes the _entire_ transitive closure server-side in a single round trip (`docs/DECISIONS.md` D-025's own reasoning for why this mechanism is SQL, not TypeScript, in the first place) — re-deriving a nested tree from it via repeated app-level queries would mean throwing away that single-round-trip design specifically to make the two resolvers' disproof shapes cosmetically match, for no correctness benefit and a real performance cost on every exclusion-touching check. A flat certificate is exactly as independently verifiable (see `verifyRelationDisproof` in `production-resolution-path.integration.test.ts`: every node's tuples are checked exhaustively against real Postgres, and every edge not continuing into another certificate node is checked against the same depth/cycle rule the SQL guard itself enforces) without forcing a shape mismatch between two resolvers whose whole value (§6.2) comes from being genuinely different implementations, not synchronized ones.
**Revisit if:** Never, for the shape mismatch itself — matches D-022's own standing precedent that the two resolvers' internal shapes are independent redeclarations, not a shared contract, and D-025's precedent that the two resolvers are allowed genuinely different algorithm shapes for the same mechanism.

## D-038 — `checks.depth` is the maximum recursion depth reached anywhere in a check, across both the TypeScript-level walk and every SQL-level recursive CTE it issued — not the depth of the winning branch alone, and not an echo of the configured ceiling

**Date:** 2026-08-15 · **Phase:** 6 · **Status:** settled
**Decision:** `ProductionCheckResult.depth` is a single mutable high-water mark (`WalkContext.depthReached`) updated at every `resolve()` entry (the TypeScript-orchestrated combinator/tuple-to-userset depth) and folded together with the deepest frontier row `sqlRelationMembershipWithWitness` actually reached on every relation-level call it made during the same check — the max of both, not a separately-reported pair and not just whichever ran last.
**Alternative rejected:** (a) Report only the depth of the final, winning (or terminal-denying) branch. (b) Report the two mechanisms' depths as two separate fields.
**Why it lost:** §4 defines `checks.depth` in one sentence — "recursion depth actually used" — with no further specification, and this is a real ambiguity in the spec worth stating plainly (see this task's own final report): "the winning branch's depth" undersells how deep a check actually searched when it explored several failing branches first (a union with three failing children before a fourth succeeds did real work at each of their depths, not just the last one), and a two-field report pushes the "how deep did this really go" judgment call onto every future caller/report renderer instead of answering it once, centrally. A single high-water mark across both mechanisms is the simplest value that's still honest about "how much of the depth budget did this check actually spend," and costs nothing extra to compute since both mechanisms already track their own depth for their own guards.
**Revisit if:** A future consumer of `checks.depth` needs to distinguish "TypeScript-side depth" from "SQL-side depth" specifically (e.g. to diagnose which mechanism is closer to exhausting its budget) — split the field then, with a real consumer driving the shape, not preemptively.

## D-039 — `buildDivergenceRecord` is extracted as its own pure, exported function specifically so the Phase 6 path-threading claim is unit-testable without Postgres or unsafely mutating a shipped resolver file

**Date:** 2026-08-15 · **Phase:** 6 · **Status:** settled
**Decision:** The `DivergenceRecord`-building logic inside `runSoundnessFuzz`'s own loop (classify, then attach `referencePath`/`productionPath` present iff that resolver's own boolean was `true`) is pulled out into `buildDivergenceRecord(input): DivergenceRecord | null`, a pure function taking already-computed booleans/paths and `classifyResult`'s own (untouched) output. `runSoundnessFuzz` now just calls it in a loop; nothing about `classify.ts`'s classification logic changed.
**Alternative rejected:** Leave the record-building logic inline inside `runSoundnessFuzz`, and satisfy `test/isolation/differential-soundness.fuzz.test.ts`'s formerly-`.todo()` resolution-path test either by (a) driving the real `runSoundnessFuzz` against a real, temporarily-broken production resolver file, or (b) leaving the test `.todo()` a while longer, pending a real Postgres-backed fixture in the `.integration.test.ts` sibling file.
**Why it lost:** (a) is exactly the practice this repo's own `test/isolation/differential-soundness.fuzz.test.ts` doc comment already rules out for its "fuzz harness has power" tests — mutating a shipped source file at test-run time is unsafe (a crash mid-mutation leaves the repo broken), not parallelizable, and not repeatable the way a committed CI test needs to be; that discipline should apply here too, not just to the tests that happened to state it explicitly first. (b) would leave a satisfiable claim un-tested past the phase that implements what it needs, which D-001 already calls a signal the phase isn't actually done. Extracting the pure function costs one small, uncontroversial refactor and makes the actual new behavior (Phase 6's field-population rule) testable the same way `classify.ts`'s own tests already work — hand-supplied inputs, no I/O, no synthetic engine needed — while a real, live differential-fuzz run against a deliberately broken engine (verified manually for this task — see the final report for the actual numbers) still covers the end-to-end claim, matching this project's own established verification discipline for Phase 5.
**Revisit if:** Never, for the extraction itself — a pure `build*Record` function factored out of an I/O-heavy orchestration loop specifically to keep it unit-testable is a pattern worth repeating, not a one-off.

## D-040 — `expand()`'s cycle guard is real production code, but its own `boundReached`-equivalent (`cycleGuard`/`depthLimitReached`) is a rendering signal, not a claim a downstream consumer needs to re-verify the way a check's `boundReached` disproof leaf does

**Date:** 2026-08-15 · **Phase:** 6 · **Status:** settled
**Decision:** `expand()`'s `cycleGuard`/`depthLimitReached` nodes are surfaced as-is in the returned tree (so a caller rendering it can show _why_ a branch stopped) with no accompanying certificate proving the cutoff was legitimate — unlike a check's resolution-path `BoundReachedDisproof`, which only ever appears inside an _allowed_ check's exclusion disproof and therefore must independently re-verify for the check's own `allowed: true` conclusion to be trustworthy.
**Alternative rejected:** Give `expand()`'s cycle/depth nodes the same certificate-level rigor as a check's `BoundReachedDisproof` (e.g. embedding the ancestor path that proves the cycle, so a consumer could independently confirm the cutoff rather than trusting `expand()`'s own bookkeeping).
**Why it lost:** `expand()` never asserts a security-relevant boolean the way a check does — it answers "who's in this set," and a `cycleGuard` node is disclosure ("this branch was cut off here, for this reason"), not a load-bearing premise of an `allowed: true` verdict that Phase 5's differential-fuzz soundness claim depends on. Nothing in §9 Phase 6's exit criterion asks `expand()`'s cycle-safety to be independently re-verifiable the way a resolution path's is — only that it terminates on a real cycle instead of hanging, which is a termination property (verified directly for this phase — see the final report's account of temporarily removing the guard and observing the walk fail to terminate within 15 seconds, versus well under a second with it intact) and a shape property (the tree the caller sees), not a proof obligation. Building a certificate here would be real, unrequested complexity for a claim nothing downstream actually needs to check.
**Revisit if:** `expand()`'s output is ever used to _drive_ an authorization decision directly (rather than shown to a human deciding whether to trust one) — at that point its cycle/depth nodes would carry the same weight a check's disproof leaves do, and would need the same rigor.

## D-041 — `runSoundnessFuzz` never routes its per-query checks through `performCheck`; only a real, application-facing check gets an audit-log row

**Date:** 2026-08-15 · **Phase:** 6 · **Status:** settled
**Decision:** `src/audit/checks.ts`'s `performCheck` (the `checks`-table-logging wrapper around `productionCheck`) has exactly one caller in this codebase: the CLI's `authz check` command. `src/soundness/runner.ts`'s `checkAllQueries` continues to call `productionCheck` directly, unchanged, exactly as it did before Phase 6.
**Alternative rejected:** Route every one of a fuzz run's `SOUNDNESS_FUZZ_QUERIES` (up to 5,000 by default) per-query checks through `performCheck` too, so the `checks` table has a complete record of literally every `productionCheck` call this system ever makes, fuzz or real.
**Why it lost:** A fuzz run's queries are checks against generated, seed-salted, synthetic fixture data (`src/soundness/generators.ts`) — they exist to test the engine, not to answer a real caller's real authorization question, and the run that produced them is already durably recorded in full as its own `soundness_runs` row (query count, every divergence, the seed needed to reproduce it byte-for-byte). Logging all 5,000 to `checks` on every run — including every CI run, per PR — would make the audit trail's actual signal (real application checks) a rounding error against synthetic noise within days, undermining the exact thing §9 Phase 6's exit criterion exists to make trustworthy: a human being able to read `checks` and understand what this system was actually asked and answered.
**Revisit if:** A future consumer needs `checks` to double as a complete `productionCheck` call log for performance/debugging purposes regardless of source — at that point, add a `source` column (`'application' | 'fuzz'`) rather than routing fuzz traffic through unconditionally, so the distinction this decision protects stays queryable rather than lost.

## D-042 — A failed `checks` audit-log write fails the whole check operation; `performCheck` never returns an unlogged answer

**Date:** 2026-08-15 · **Phase:** 6 · **Status:** settled
**Decision:** `performCheck` computes the real answer via `productionCheck` first, then inserts the `checks` row; if that insert throws, `performCheck` itself throws — the already-computed `allowed`/`path` result is discarded, never returned to the caller. In the CLI, this surfaces exactly like any other infrastructure failure: exit 3, not a printed answer.
**Alternative rejected:** Catch a logging failure, `console.error` or otherwise note it, and still return the real, correctly-computed answer — "best-effort" audit logging that never blocks a caller who just wants to know if a permission is granted.
**Why it lost:** §9 Phase 6's exit criterion states "every check, allowed or denied, is logged" with no qualifier — not "every check that could be logged," not "logged when convenient." A caller who received `ALLOWED` from a check whose audit-log write silently failed would have a real, unrecorded grant decision — exactly the kind of gap that makes `docs/RELATIONS.md`'s and this project's own audit-trail claim (§6.7: "every allow decision records the path that justified it") an overstatement rather than a fact the moment it happens even once. `productionCheck` itself already draws this same line for a genuinely unreachable database (throws, never returns a smoothed-over `false`) — treating a failed audit write any more gently than a failed read would be an inconsistent standard applied to the same underlying database, for no principled reason.
**Revisit if:** A real deployment needs check _availability_ to survive a temporary audit-log outage (e.g. `checks`' own disk/partition full while `relation_tuples` is healthy) — that's a legitimate, different tradeoff (availability over completeness) a future phase could opt into explicitly (e.g. a `--best-effort-audit` flag), but it must be an explicit opt-in with its own stated risk, not this function's silent default.

## D-043 — A non-linear resolution path (`intersection`/`exclusion` anywhere in the tree) renders inside a fenced plain-text block, never a native nested markdown list

**Date:** 2026-08-15 · **Phase:** 7 · **Status:** settled
**Decision:** `src/report/markdown.ts`'s `renderPathBlock` renders a fully linear proof (`directGrant`/`usersetMembership`/`tupleToUserset`/transparent `union` only) as one `→`-joined chain line, exactly §8's worked example. The moment an `intersection` or `exclusion` appears anywhere in the tree, the whole path renders instead as one fenced ` ```text ` block (plain text, no markdown syntax inside it), with the closing `_(this proves ...)_` annotation as its own separate markdown paragraph directly below the fence, never on the fence's own last line.
**Alternative rejected:** A native, indented markdown list (`- `/numbered, nested per combinator) for the structured case — the first draft built.
**Why it lost:** Verified by actually rendering the first draft's output through a real markdown parser (`markdown-it`), not by inspection: GitHub-flavored markdown's lazy-continuation rule silently folds a sibling line that isn't blank-line-separated and isn't itself a new list marker into the _previous_ list item's own content. This swallowed the renderer's own "excluding:" label and its closing "(this proves ...)" annotation into the wrong branch of the tree — a structural corruption of exactly the evidence this file exists to render faithfully, and precisely the kind of failure mode a `false_grant`'s resolution path (§6.7, §8) can least afford, since it's the one piece of output a reader is meant to trust literally. A fenced code block sidesteps GFM's list-nesting rules entirely (its content is never markdown-parsed), at the deliberate cost of losing inline bold/code emphasis inside the tree itself.
**Revisit if:** Never for the mis-nesting risk itself (that's inherent to GFM, not a fixable renderer bug). Revisit the code-fence tradeoff specifically if a future phase's UI (§8's actual screens, Phase 9) needs richer inline styling inside a non-linear resolution path — a real DOM-rendered tree component wouldn't carry GFM's own list-nesting hazard the way a markdown string does, and could use markdown-style nested lists safely.

**Date:** 2026-08-15 · **Phase:** 7 · **Status:** settled
**Decision:** The one reserved treatment for `false_grant` throughout `src/report/markdown.ts` is `**FALSE_GRANT**` — bold, all-caps, backticked entity references around it — never an emoji anywhere in this file's output.

## D-045 — `.github/workflows/soundness.yml` runs its own ephemeral Postgres `services:` container, never `secrets.DATABASE_URL`

**Date:** 2026-08-15 · **Phase:** 7 · **Status:** settled
**Decision:** The soundness workflow provisions a fresh `postgres:16-alpine` GitHub Actions `services:` container per run and points `DATABASE_URL` at it — never the real, long-lived Railway database this project's own `DATABASE_URL` secret (if configured) would point to, even though §7's own YAML stub literally shows `env: DATABASE_URL: ${{ secrets.DATABASE_URL }}`.
**Alternative rejected:** Follow §7's literal YAML — run the soundness fuzz against the real, shared project database via `secrets.DATABASE_URL`.
**Why it lost:** The standard fuzz budget writes up to `SOUNDNESS_FUZZ_QUERIES` (5,000 by default) worth of generated namespaces and tuples into `relation_tuples`/`namespace_configs` on every single run, on every PR, forever. Against a real, long-lived database, none of that data is ever cleaned up (D-033's seed-salting prevents cross-run _correctness_ collisions, but does nothing about accumulation) — a project with even modest PR volume would see its real database grow by tens of thousands of synthetic rows a week, purely as a side effect of CI existing. `ci.yml`'s own `test-integration` job already establishes the right precedent for this project: a disposable, per-run Postgres instance for anything that writes real rows during a test, never the shared project database (testcontainers there, since that job is a set of Vitest files that can start their own container in-process; a native `services:` container here, since `authz soundness run` is a plain CLI invocation with nothing to start a container itself).
**Revisit if:** A future phase wants to track soundness-run history _across_ runs in one persistent place (e.g. a dashboard of every PR's fuzz result over time) — that's a real, different requirement (durable `soundness_runs` history) this decision doesn't provide for, and would need its own design (e.g. a separate, dedicated reporting database this workflow writes a summary row to, distinct from the disposable database it fuzzes against).

**Date:** 2026-08-15 · **Phase:** 7 · **Status:** settled
**Decision:** `npm run build` now runs `node scripts/copy-migrations.mjs` after `tsc`, copying `src/store/migrations/*.sql` to `dist/store/migrations/`.
**Alternative rejected:** None seriously considered — this is a bug fix, not a design tradeoff. (The nearest real alternative, resolving `MIGRATIONS_DIR` against `src/` instead of the compiled file's own location regardless of build vs. source, was rejected because it would make the _built, distributed_ CLI depend on a `src/` directory being present alongside `dist/` at runtime — wrong for anything actually installed as a package, and not how `src/cli/commands/doctor.ts`'s existing `new URL('../../store/migrations', import.meta.url)` pattern is meant to work.)

**Revisit if:** Any future build output (an npm-published package, a Docker image) also needs these files — `scripts/copy-migrations.mjs` already handles the general case (copies the whole `migrations/` directory, not one file at a time), so this should already cover that; revisit only if a packaging format needs the files somewhere other than alongside the compiled `store/` output.

## D-049 — The API is unversioned, flat, and RPC-shaped (`POST /check`, `POST /expand`), not a REST resource model

**Date:** 2026-08-15 · **Phase:** 8 · **Status:** settled
**Decision:** Every route is `POST` (or `DELETE /tuples` for the one delete), named after the CLI operation it mirrors (`/check`, `/expand`, `/tuples`, `/schema/compile`, `/schema/publish`, `/health`), with no `/v1/` prefix and no resource-oriented nesting.
**Alternative rejected:** A conventional REST shape — `GET /checks?subject=...&relation=...&object=...` for a read-only check, `POST /v1/tuples` with a versioned prefix, `201 Created` + `Location` header for a tuple write.
**Why it lost:** §9 Phase 8's own wording is "exposing check/expand/write/schema _per the CLI's own operations_" — an RPC shape, not an invitation to invent a resource model this system doesn't have. `check`/`expand` both take a structured, nested query (`subject`/`object` as `{ns,id}` pairs) that a flat GET query string would force apart with no benefit (no caching layer exists to reward `GET`'s cacheability). **Revisit if:** This API grows a genuine caller outside this repo's own CLI/tests, at which point both a stable version prefix and `GET`-for-reads (for caching/idempotency semantics real HTTP infrastructure understands) become worth their cost.

## D-050 — An unconfigured `ADMIN_API_KEY` fails every write closed, never open

**Date:** 2026-08-15 · **Phase:** 8 · **Status:** settled

## D-054 — The `ADMIN_API_KEY` comparison uses `crypto.timingSafeEqual`, not `===`

**Date:** 2026-08-15 · **Phase:** 8 · **Status:** settled
**Decision:** `src/api/auth.ts` compares the supplied bearer token against `env.ADMIN_API_KEY` with `node:crypto`'s `timingSafeEqual` (after a length check, which `timingSafeEqual` itself requires — unequal-length buffers throw rather than compare), never JavaScript's `===`/`string.length` short-circuiting comparison.
**Alternative rejected:** A plain `supplied === env.ADMIN_API_KEY` string comparison — simpler, and correct for every functional test in this phase's own suite (which can't distinguish the two by response _content_, only by response _timing_).
**Why it lost:** `===` on strings short-circuits at the first mismatched character, which means comparison time correlates with how many leading bytes of a guess happen to match the real key — a timing side channel an attacker with enough network samples can exploit to recover the key byte-by-byte without ever seeing a successful response. This is a single-admin-key HTTP API with a real, if narrow, network attack surface (anyone who can reach the deployed service can attempt this), so the standard mitigation (compare in an order-independent, data-length-only-dependent way) costs nothing here — `timingSafeEqual` is a Node built-in, not a new dependency — and directly closes a known class of vulnerability class that a purely functional test suite would never catch (every test that supplies a correct or incorrect key gets the right _answer_ either way; only a timing measurement would show the difference, which this project doesn't have infrastructure to test for, making prevention-by-construction the only real option here).
**Revisit if:** Never, for a secret-comparison path — this is close to a strict-dominance choice (no real downside) rather than a tradeoff to revisit.

## D-056 — `@fastify/rate-limit` added to close a real CodeQL finding, per explicit user approval

**Date:** 2026-08-15 · **Phase:** 8 · **Status:** settled
**Decision:** `@fastify/rate-limit` added as a real dependency (outside build spec §2's stated stack, so asked first per rule 6 — approved). Registered globally on the Fastify instance with a 100-request/minute default, overridden per-route: 300/minute on `GET /health` (real load-balancer polling needs headroom), 20/minute on the three `ADMIN_API_KEY`-gated write routes (defense-in-depth against key-guessing and write-flooding even from a caller who holds a valid key). A dedicated `rate_limited` `ApiErrorCode` (429) was added to `src/api/errors.ts` (same additive pattern as D-052's `invalid_request`) so a rate-limited response carries this API's one standard error envelope, never the plugin's own default body shape.
**Alternative rejected (build vs. buy):** A small in-house in-memory per-IP limiter — offered as an option specifically to avoid a new dependency. Rejected by explicit user choice: the standard, actively-maintained Fastify-official package is the better tradeoff here (correct edge cases — IPv6 subnetting, draft-spec headers, ban thresholds — that a from-scratch implementation would either skip or have to re-derive and re-test) for a security-relevant control that's cheap to get from a well-audited source.
**A real, non-obvious integration bug found and fixed while wiring this in, not by reading documentation alone:** registering the plugin via a fire-and-forget `void app.register(rateLimit, opts)` immediately followed by synchronous route declarations (the pattern every other registration/hook call in this file already uses) silently produced a rate limiter that never limited anything — confirmed live via a minimal reproduction outside this codebase entirely (a bare `Fastify()` instance, `@fastify/rate-limit`, one route, six requests, real sockets via `fetch`, not `.inject()`): zero `x-ratelimit-*` headers, zero `429`s, at any request count, with no error raised anywhere. Fastify only wires a plugin's `onRoute` hook (how `@fastify/rate-limit` attaches itself to each route) once that plugin's own async registration has actually resolved; declaring routes synchronously right after an un-awaited `.register()` call races that resolution and the routes are built before the hook exists to catch them — with the plugin's own `settings` (max/timeWindow) accepted silently, giving no signal anything was wrong. Fixed by making `buildServer` itself `async` and `await`-ing the one `app.register(rateLimit, ...)` call before any route is declared. A second, related bug surfaced immediately after fixing the first: `@fastify/rate-limit`'s `errorResponseBuilder` option is a value to `throw`, not a response body to return (its own default implementation returns a real `Error` with `.statusCode` set) — returning `rateLimitedError(...).body` directly from it, as if it worked like every other constructor in `src/api/errors.ts`, got the object thrown as a non-`Error` value and fell through to this file's own generic `>= 500` `internalError()` branch, misreporting a rate limit as a `500` instead of a `429`. Fixed by returning a real `Error` carrying a `retryAfterSeconds` marker, recognized and reshaped into `rateLimitedError`'s own envelope inside `setErrorHandler`.
**Independently verified, not trusted from the fix alone:** a dedicated `test/unit/api/rate-limit.test.ts` (written directly, not delegated — a small, focused addition responding to a CI finding discovered after both `test-author` Phase 8 passes had already completed) sends 21 real requests to a write-gated route and asserts the first 20 never return `429` while the 21st does, with the standard `rate_limited` envelope; a sibling test sends 20 requests to an unauthenticated read route and confirms none trip the (much higher) global default, proving the per-route override is real and not just a higher global number. Also confirmed against the real built CLI (`npm run build && node dist/cli/index.js serve`) against real local Postgres — real `x-ratelimit-limit: 300`/`x-ratelimit-remaining: 298` headers on a real `GET /health` request.
**Revisit if:** A future deployment runs multiple instances behind a shared load balancer — this plugin's default in-memory store is per-process, so the effective limit multiplies by instance count; `@fastify/rate-limit` supports a Redis-backed store for that case (`RedisStore`, already bundled in the package), not yet needed for this project's own stated single-instance, non-distributed scope (§1's own non-goals).
