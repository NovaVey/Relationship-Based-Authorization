Tuple browser

All 22 relation tuples currently written to the seeded demo graph — the facts the check engine walks, never a conditional in application code. Grouped by the object's namespace, in the same order the demo seeds them (scripts/seed-example.ts): org membership first, then nested groups, then the folder hierarchy, then documents.

A tuple is a fact, not a derived permission — view and edit never appear as a relation column value here because a permission can never be the target of a tuple write (build spec §5). See the Namespaces screen for how these tuples get combined into computed permissions.

4 tuples

folder:eng_docs grants editor directly to group:eng#member. folder:eng_backend_docs holds only a parent tuple pointing at eng_docs — no direct grant of its own at all; everything on it is inherited via parent→edit / parent→view, proving inheritance actually does the work rather than sitting behind a direct grant as a fallback. folder:finance_docs splits ordinary access (viewer to group:finance#member) from a narrower sensitive_reviewer grant held by user:carol alone — the two branches the sensitive_review intersection checks (see Namespaces).
