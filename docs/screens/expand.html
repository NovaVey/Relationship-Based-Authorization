Expand tree

The full subject tree for one object#relation — mirrors authz expand <object> <relation> (build spec §7). Where the check playground shows the single path one subject actually walked, this shows every route to the relation at once: every union branch, every intersection requirement, every tuple-to-userset hop, and every nested group membership that contributes a subject — including the ones that contribute none.

Two real trees below, captured from this project's own expand() against the seeded demo graph: document:eng_handbook#edit — union and tuple-to-userset, with a group nested two levels deep — and folder:finance_docs#sensitive_review — an intersection, the one shape where both branches have to independently produce a member for it to matter. Per build spec §9 Phase 9, the first exists so the demo proves tuple-to-userset actually works, not just direct grants.

How to read this tree

Five things appear in the trees below. Each is marked by a text label first — color is never the only signal.

  • ∪union

    Rewrite rule | in the DSL (§5). Any one child branch producing a subject is enough — editor | owner | parent→edit.

  • ∩intersection

    Rewrite rule & in the DSL (§5). Every child branch must independently produce the same subject — (viewer | edit) & sensitive_reviewer.

  • tupleToUserset

    Rewrite rule parent->edit in the DSL (§5). Follow a stored relation tuple to a different object, then recurse into a permission or relation there.

  • relation

    A leaf lookup: which subjects actually hold this exact relation on this exact object, right now, as stored tuples — either direct, or because a tuple's subject is itself another object's userset.

  • direct

    A plain tuple subject — user:alice, not a userset.

  • userset subject

    Not a rewrite rule — a fact about one tuple's own subject field (group:eng#member naming another relation as the subject). This is what makes nested group membership work with zero special-cased recursion (§5).

Exclusion (a - b, e.g. org.view = member - banned) does not appear in either tree on this screen — neither document:eng_handbook#edit nor folder:finance_docs#sensitive_review is built from one. The demo's one real exclusion case is the Check playground screen's user:mallory view org:acme result (denied: banned overrides membership). Rather than fabricate an exclusion node here, this page shows honestly that neither captured tree exercises one.

Reading the tree above against two real checks against this same object and relation: carol appears as a direct subject in both required branches — group:finance#member (via branch 1) and sensitive_reviewer directly (branch 2) — so the intersection resolves allowed for her. erin appears only in branch 1 (group:finance#member); she holds no sensitive_reviewer tuple on folder:finance_docs, so branch 2 produces nothing for her and the intersection resolves denied — the two-people, one-tree case the DSL note in schema/example.authz names directly: "two people can both be ordinary viewers of the same folder and get different answers to this one permission."
