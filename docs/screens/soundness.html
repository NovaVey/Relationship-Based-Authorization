Soundness runs

Every run below is real output from authz soundness run — differential fuzzing of the production check engine against the independent reference resolver (build spec §6.2), captured against this repo's own database. Nothing here is a mockup number: two independent runs, both verdict sound, both 0 false_grant, 0 false_deny, across 5000 queries each.

0 false_grant is reported here as a measured result of each run's own fuzz budget — not as a claim that the system "is secure." A wider budget, or a different seed, could in principle find something these two runs didn't; that's why the seed and the reproduce command are shown for each, not summarized away.

Reading a soundness run

The verdict is asymmetric by design (build spec §6.5) — a false_grant (production allowed, the reference resolver found no path) is a security bug and fails the run unconditionally; a false_deny (production denied despite a real path existing) is a correctness bug, reported and counted, but never blocks on its own. Visual weight here follows that asymmetry, not the reverse:

  • FALSE_GRANT the one hard alert color on this page, reserved only for this. It never appears anywhere else here — not for a warning, not for a denial, not for anything but an engine that allowed something with no real path behind it.
  • false_deny muted, bordered, never filled — visible, never buried, but never competing with a FALSE_GRANT for attention.
  • SOUND neutral ink, no color claiming safety — a verdict, not a celebration. Plain ink is also what unsound and insufficient_coverage render in; only the divergence entries inside an unsound run's report carry the alert color, never the verdict word itself.

Exit codes this run's CLI/CI invocation maps to (build spec §7) — a false_grant and an infrastructure failure are never conflated:

  • 0 sound, no issues
  • 1 a false_grant (or any checks audit failure)
  • 2 insufficient fuzz coverage or a schema/tuple validation failure
  • 3 infrastructure failure (DB unreachable, etc.)

Illustrative example — not a real finding

If a FALSE_GRANT were found

Neither run above found one — 0 across 10,000 combined queries. Nothing on this page up to this point is a false_grant. This panel exists only to show how this project's own report renders one, so the convention is legible before it's ever needed for real.

The scenario below is hand-constructed, not sampled from any run: the kind of bug Phase 5's own exit criteria require the fuzz harness to catch by deliberately introducing it — "skip an intersection branch" (build spec §9 Phase 5) — applied here to org's real view = member - banned exclusion (build spec §5, seen on the Namespaces screen). If the subtract branch were skipped, production would allow a query the reference resolver correctly denies.

FALSE_GRANT user:mallory view org:acme
field value
expected (reference resolver) denied — no path (member minus banned; mallory fails the subtract)
actual (production, in this hypothetical) allowed
class false_grant — critical (fails the run unconditionally)

Resolution path production would have to claim

user:mallory → org:acme#member → org:acme#view

This chain never touches the exclusion's subtract branch — it proves membership and stops. That's the bug being illustrated: an engine allowed via a path that doesn't actually exist once banned is accounted for. The real, current build's answer to this exact query is denied, depth 1, no path (.captures/check-mallory-view-org.json) — that is what actually runs today; the chain above is what would have to appear if this specific bug shipped.

A false_deny, if one were found, would render with the false_deny muted badge above instead — same divergence-card shape, same resolution path (a real one exists; production just missed it), never the alert color. It's reported and counted, and it never fails the run by itself (build spec §6.5).
