Check playground

Run a check — subject, relation, object — against the seeded demo graph, and see either the resolution path that produced allowed, or the concrete reason it didn't. A permission is never granted because it looks like it should be: it resolves because of a specific, walkable chain of tuples, or it doesn't.

Checks in this demo run against the schema versions in GET /health — document v1, folder v1, group v1, org v1 (.captures/health.json).

Run a check

Mirrors authz check <subject> <relation> <object> [--at-token <n>] (build spec §7). Fields accept namespace:id — the datalist suggestions below are real ids and relation names from the seeded demo graph, not placeholders.

Query

Pins the read to a token from a prior write (§6.3). Left blank, the check reads current committed state.

user:dana edit document:eng_handbook

allowed union · tuple-to-userset · nested groups

depth 3 — recursion depth actually used, per the real POST /check response.

Resolution path — 5 tuples chained together
user:dana → group:eng_backend_interns#member → group:eng_backend#member → group:eng#member → folder:eng_docs#editor → document:eng_handbook#edit

This is build spec §9 Phase 9's own named non-obvious case: dana's only route to this permission runs through two levels of group nesting before the parent→edit hop ever fires. group:eng_backend_interns#member has dana as a direct tuple; group:eng_backend#member names group:eng_backend_interns#member as its own subject; group:eng#member names group:eng_backend#member as its subject in turn. document:eng_handbook's parent relation points at folder:eng_docs, and folder:eng_docs grants its editor relation to group:eng#member directly — so document.edit's union (branch 3, parent→edit) recurses into folder.edit, which resolves through that editor grant.

user:mallory view org:acme

denied exclusion

depth 1 — recursion depth actually used, per the real POST /check response.

No resolution path — a denial doesn't produce one; checks.resolution_path is only populated when allowed is true (§6.7). The reason is the exclusion's own two branches:

org.view compiles to member −not banned. Both tuples exist for mallory:

object relation subject
org:acme member user:mallory
org:acme banned user:mallory
  • ✓ matched base branch member — org:acme#member@user:mallory exists; on its own this branch would resolve allowed.
  • ✓ matched subtract branch banned — org:acme#banned@user:mallory exists; an exclusion (a - b) resolves allowed only if the base matches and the subtract branch does not. Here it does, so the exclusion nets to denied.
Raw compiled rewrite — org.view 
{
  "kind": "permission",
  "name": "view",
  "rewrite": {
    "kind": "exclusion",
    "base": { "kind": "computedUserset", "name": "member" },
    "subtract": { "kind": "computedUserset", "name": "banned" }
  }
}

  "subject": { "ns": "user", "id": "mallory" },
  "relation": "view",
  "object": { "ns": "org", "id": "acme" },
