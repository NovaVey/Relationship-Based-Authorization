Reading a permission

A permission is never itself the target of a tuple write — it's computed from relations by one rewrite rule. Rendered expressions below use → for a tuple-to-userset hop; the DSL source itself writes that as -> — see each namespace's own source excerpt for the exact syntax.

  • | union allowed if any operand resolves.
  • & intersection allowed only if every operand resolves.
  • - exclusion allowed if the left operand resolves and the right does not (a - b).
  • rel → perm tuple-to-userset: follow rel to another object, then recurse into its perm.
  • direct reference not one of the four rewrite operators — the permission is exactly the named relation, nothing combined.
Filter by kind:

De-emphasizes permissions that don't use the selected kind(s) — nothing is hidden, everything stays in the document. Works without JavaScript too: with it disabled, the buttons are inert and every permission stays fully visible.

DSL source — schema/example.authz 
namespace org {
  relation member: user | group#member
  relation banned: user

  // Anyone in the org can see org-wide content — unless explicitly banned.
  // A real exclusion: `member` alone is not the answer, `member - banned`
  // is. See docs/RELATIONS.md for why this is the rewrite rule that
  // actually needs a subtract, not a second boolean column on `member`.
  permission view = member - banned
}

DSL source — schema/example.authz 
namespace group {
  // `user | group#member` is what makes nested group membership possible
  // with zero special-cased recursion: a tuple can name another group's
  // *member set* as its subject
  // (`group:eng#member@group:eng_backend#member`), not just a plain user.
  // See docs/RELATIONS.md's own walkthrough of the seeded graph's
  // two-level nesting case.
  relation member: user | group#member

  permission view = member
}

Permissions

Editing a parent folder implies editing everything nested under it — parent→edit, never parent→view (an edit permission that only required the parent's view would be a privilege-escalation bug, not a convenience). sensitive_review intersection
( viewer |or edit ) &and sensitive_reviewer

Being able to see this folder at all is necessary but not sufficient — you also need the narrower sensitive_reviewer grant. Two ordinary viewers of the same folder can get different answers here.

Real example — same folder, two outcomes (check-carol-…, check-erin-…)

  • ✓ satisfied viewer | edit — via user:carol → group:finance#member → folder:finance_docs#viewer
  • ✓ satisfied sensitive_reviewer — direct grant user:carol → folder:finance_docs#sensitive_reviewer

DSL source — schema/example.authz 
namespace folder {
  relation parent: folder
  relation owner: user
  relation editor: user | group#member
  relation viewer: user | group#member
  // Who's specifically cleared to review this folder's sensitive
  // contents — deliberately a *second*, narrower gate on top of ordinary
  // access, not a replacement for it. See `sensitive_review` below.
  relation sensitive_reviewer: user | group#member

  // Editing a parent folder implies editing every folder/document nested
  // under it — `parent->edit`, never `parent->view` (an edit permission
  // that only required the parent's *view* would be a real privilege-
  // escalation bug, not a convenience).
  permission edit = editor | owner | parent->edit
  // Anyone who can edit can also view; direct viewers can view; and view
  // inherits down the folder tree the same way edit does.
  permission view = viewer | edit | parent->view
  // Intersection: being able to see this folder at all is necessary but
  // not sufficient — you also need the narrower `sensitive_reviewer`
  // grant. Two people can both be ordinary viewers of the same folder and
  // get different answers to this one permission.
  permission sensitive_review = (viewer | edit) & sensitive_reviewer
}
